# Browser grant binding with DPoP

Research, 2026-10-28. Proposed; no implementation or accepted ADR.

The [credential model](../plan/credentials.md) currently relies on exact-origin checks and bearer credentials. A non-browser client can copy the token and supply that origin. The proposed improvement binds each browser grant to a private key established during pairing. It constrains copied-token use; browser attestation and misuse of the signing key remain outside scope.

Prefer **A, a private WebSocket proof item**, preserving existing upgrade/resume paths. **B, a socket challenge**, provides stronger connection-specific binding at the cost of another authentication state machine. **C, a bootstrap ticket**, alone leaves a short-lived bearer credential that can be raced if stolen. The transport choice remains open.

1. **Pairing and key lifetime.** Generate a fresh ES256/P-256 key for each pairing, with a non-extractable private key. Persist the CryptoKey in IndexedDB before PAR; put its random reference in the session-scoped transaction and grant. Open consent popups synchronously before asynchronous key work. Compute the public-key [RFC 7638 thumbprint](https://www.rfc-editor.org/rfc/rfc7638.html#section-3), then carry it unchanged through pending authorization, code and persisted grant. Never establish or replace this binding during redemption. Preserve PKCE, the approved issuer/application origin, fixed tools, profile and grant epoch.

2. **Standard HTTP mechanism.** RFC 9449 requires PAR+DPoP servers to support both `dpop_jkt` in the PAR POST body and the `DPoP` proof header. A header proof binds the code to its key; supplying both requires matching keys. Clients need not send both. Checks include a single proof, `typ=dpop+jwt`, acceptable asymmetric algorithm, public-only embedded JWK, signature, `jti`, `htm`, normalized `htu` excluding query/fragment, freshness and required nonce. Access-token use additionally checks `ath` and the bound key. Public-client refresh tokens require same-key proofs. Standard protected HTTP requests use `Authorization: DPoP` and `DPoP` headers. Token responses identify bound access tokens with `token_type: DPoP`. DPoP does not sign `Origin` or request bodies. Production requires HTTPS. [RFC 9449 §§4–10](https://datatracker.ietf.org/doc/html/rfc9449)

   Proposed SDK policy: send the proof-header PAR form and reject unbound token responses. Continue comparing each request's application origin with the approved grant. Build expected request URIs from configured entry points and the actual endpoint, never untrusted forwarding headers. Advertise ES256 support, allow the DPoP request header through CORS, and expose nonce/authentication response headers.

3. **Verification and state changes.** Use a reviewed, pinned Rust verifier. Bound JWT/JWK inputs, reject ambiguous members and unsupported critical headers, and never fetch supplied key URLs. Proposed starting policy: 60-second proofs, small clock tolerance, mandatory short-lived unpredictable nonces, and an atomic replay cache scoped by issuer, key and proof identifier. Keep entries for the full acceptance window and fail closed at capacity. Invalidate old nonce contexts across restart; separate authorization-server and WebSocket contexts.

   Verify possession **before consuming a code, rotating credentials, or revoking a grant for spent-refresh reuse**. Otherwise a copied spent token could still revoke the legitimate grant. Require same-key proof for application revocation as a documented gateway extension; owner revocation remains separately authorized. Bind token hashes and key metadata atomically.

4. **WebSocket transport alternatives.** The browser API exposes URL/subprotocol arguments, but no arbitrary headers or failed-upgrade HTTP response details. Its handshake maps `wss` to HTTPS and generates `Sec-WebSocket-Key` internally. [WHATWG WebSockets](https://websockets.spec.whatwg.org/) Compact JWT characters fit the subprotocol token grammar; authentication through such an item remains a private convention. [RFC 6455 §§4.1–4.3](https://datatracker.ietf.org/doc/html/rfc6455#section-4.1)

   - **A: proof at upgrade.** Require exactly one private access-token item and one private proof item; echo only the selected application protocol. Before grant activation or host allocation, check the key, token hash, proof freshness/replay and WebSocket nonce, with `htm=GET` and the external HTTPS `/acp` URI. Retain origin checks. Fetch nonces through a bounded credential-free HTTP endpoint with CORS/no-store and no grant mutation. This reuses the verifier/cache and leaves session frames unchanged. A stolen token plus an unused proof can win the first-use race; this provides no socket binding. Bound combined header size, test supported intermediaries, and redact credential items from logs. HTTP defines no universal header-size ceiling. [RFC 9110 §5.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.4)
   - **B: socket challenge.** Upgrade into bounded unauthenticated state. Send a socket-specific nonce and require a distinctly typed signed response covering nonce, token hash, issuer/origin and attach/resume intent before host lookup/allocation. A proof captured for another socket fails. This is application connection binding, not TLS channel binding, and does not defeat a live signing oracle. Challenges/errors are readable frames; credentials leave handshake headers but still require frame-log redaction. Both transport modes need authentication states, deadlines and unauthenticated capacity limits.
   - **C: HTTP bootstrap ticket.** Authenticate ticket issuance with standard HTTP DPoP. Issue a short-lived, single-use ticket bound to issuer/origin, grant epoch, access expiry and attach intent; issuance must allocate no host. Fetch exposes nonce/errors and the socket needs only a small ticket. Ticket storage, expiry and atomic redemption add machinery. A copied ticket remains usable in a first-use race: storing its key thumbprint does not prove possession. Adding a socket proof combines C with A or B.

5. **Failure recovery and compatibility.** HTTP `use_dpop_nonce` challenges carry `DPoP-Nonce`; browser clients need that header exposed through CORS. [RFC 9449 §§8–9](https://datatracker.ietf.org/doc/html/rfc9449#section-8) Permit one fresh-proof retry only after an explicit rejection guaranteed to precede mutation. For A, an HTTP upgrade refusal is opaque and permits no automatic nonce retry. Readable stale-nonce recovery would instead require a bounded unauthenticated upgrade-only rejection branch that sends a custom close code: no grant activation, host allocation, attachment or incoming frames accepted. This adds connection-capacity and deadline handling. Only that explicit signal permits a fresh nonce fetch and proof, without refresh rotation; choose this branch or opaque refusal explicitly. B challenges on the socket; C must distinguish ticket issuance from uncertain redemption. Never replay an uncertain refresh, prompt or application effect. Re-sign reconnect attempts while preserving resume identity, acknowledgements and one active conversation request.

   Add asynchronous key storage/signing to the SDK; retain session token isolation. Missing keys require explicit re-pairing, never silent downgrade. Attempt revocation before deleting a usable key; local clearing cannot claim remote revocation. Non-extractability does not prevent XSS signing, structured-clone sharing or privileged storage access. [WebCrypto §§5–6](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/#security-considerations)

6. **Decisions and validation.** Decide A/B/C and rejection behavior, wire/error names, legacy/headless migration, key retention/tab ownership, verifier, limits and HTTP-loopback policy. Record the security decision against [ADR 0016](../decisions/0016-acp-application-boundary.md) before implementation. Keep custom carriage explicitly unstable and within existing ACP/resume; a second session protocol requires its own decision. Require no gateway preregistration or new CSP-origin allowlist.

   Test real browser WebCrypto/IndexedDB against the shipped verifier: both PAR forms/mismatch, reload/popup/redirect, wrong bindings, replay races, refresh ordering, restart, nonce rejection without consumption, storage loss, header limits, failed-upgrade opacity, authentication before allocation, and resume/unknown outcomes. Cover Chromium, Firefox and WebKit; doubles serve deterministic faults only.

Implementation seams: `crates/gateway/src/authorization.rs`; `crates/gateway/src/bin/agent-connect.rs` (`upgrade`, `serve_socket`); `packages/web-sdk/src/acp-pairing.ts`, `acp-provider.ts`, and `resumable-acp-stream.ts`.
