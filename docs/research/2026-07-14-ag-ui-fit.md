# AG-UI as the application-facing standard

Date: 2026-07-14

Status: promising pending exploration; not adopted.

## Question

Agent Connect needs an application-facing protocol that is agent- and
harness-neutral, supports streaming runs and application-defined tools, and
does not force every runtime to expose OmniGENT or Codex-specific types. The
project also needs runtime enrollment, per-application authorization, secure
remote transport, durability, and adapter-owned orchestration.

The question is whether AG-UI can provide the standard application/agent
language while Agent Connect supplies the missing user-owned-runtime security
and reliability profile.

## Findings

### AG-UI closely matches the application interaction surface

[AG-UI](https://docs.ag-ui.com/) defines an open, event-based protocol between
user-facing applications and agent backends. Its model includes runs, messages,
streamed lifecycle and text events, tool-call events, state, and
human-in-the-loop interactions. It is transport-agnostic and documents HTTP
SSE, WebSocket, and other delivery mechanisms.

Most importantly for Agent Connect, AG-UI explicitly supports
[frontend-defined tools](https://docs.ag-ui.com/concepts/tools): the application
passes JSON-Schema tool definitions with a run, receives correlated tool-call
events, executes the operation in the frontend, and returns a tool-result
message. This is the central Agent Connect capability and does not require the
tool to be preinstalled as an MCP server in the downstream agent.

The current Agent Connect event vocabulary has a direct conceptual mapping:

| Agent Connect prototype    | AG-UI concept                  |
| -------------------------- | ------------------------------ |
| `task.started`             | `RUN_STARTED`                  |
| `text.delta`               | text message start/content/end |
| `tool.requested`           | tool-call start/arguments/end  |
| application handler result | tool-result message            |
| `task.completed`           | `RUN_FINISHED`                 |
| `task.failed`              | `RUN_ERROR`                    |
| logical session            | thread                         |
| active task                | run                            |

### AG-UI does not orchestrate Codex

AG-UI standardizes the frontend/backend interaction. It does not launch Codex,
bridge the user's Codex authentication and configuration, manage a workspace,
supervise a process, create or heal an OmniGENT runner, translate ACP into Codex
app-server, or persist an unresolved side effect.

As of this investigation, the official AG-UI integration surface did not list
a maintained Codex or ACP integration. Agent Connect would implement an
AG-UI-to-OmniGENT gateway adapter. OmniGENT would continue to own conductor and
harness lifecycle, while `codex-acp` would continue to translate ACP into Codex
app-server.

```text
web application
  -> AG-UI plus Agent Connect security profile
Agent Connect gateway
  -> OmniGENT Sessions API adapter
OmniGENT
  -> ACP
codex-acp
  -> Codex app-server
Codex
```

### AG-UI does not define the required trust model

AG-UI documents middleware as the place for cross-cutting concerns including
authentication and rate limiting. It does not define how an arbitrary hosted
application verifies that a remote gateway was enrolled by its current user,
how that gateway verifies the calling user and origin, or how an accountless
runtime key is paired and revoked. See the
[AG-UI middleware model](https://docs.ag-ui.com/concepts/middleware).

That is not a defect in AG-UI; it is a different layer. Agent Connect's
contribution can be an open security and reliability profile around AG-UI:

- a portable runtime card containing routing hints and gateway identity;
- mutually authenticated gateway enrollment;
- a one-time human pairing ceremony or account-backed certificate;
- exact-origin, app-key, tool/scope, and expiry-bound authorization;
- an authenticated encrypted application channel;
- stable action identifiers and durable unresolved-action recovery;
- harness-neutral runtime adapters and health management;
- revocation, rotation, and auditable authorization decisions.

MCP's OAuth-based authorization profile is useful precedent for protected
resource discovery and client authorization, but it authenticates access to an
MCP resource rather than solving user-owned gateway enrollment. ACP's normal
architecture assumes a trusted client talking to a trusted agent and remains a
strong downstream harness interface, not the complete remote trust envelope.

## Comparison with the working OmniGENT path

The current browser SDK constructs an OmniGENT provider, opens proxied
OmniGENT SSE, posts OmniGENT message and function-result events, and maps them
into a small custom task vocabulary. The gateway provisions and heals the
opaque downstream OmniGENT session.

An AG-UI adoption would move the provider-specific mapping from the browser to
the gateway:

```text
today:
  browser SDK -> OmniGENT-shaped gateway routes -> OmniGENT

candidate:
  browser SDK -> AG-UI gateway endpoint -> OmniGENT adapter -> OmniGENT
```

The already-proven composition remains valuable. AG-UI would standardize the
left side; it would not replace OmniGENT's backend heavy lifting.

## Product positioning

A credible product statement is:

> Agent Connect is a secure user-owned-runtime profile and gateway for
> AG-UI-compatible web applications, with adapters that let existing agent
> harnesses participate. The reference composition uses OmniGENT, ACP, and
> Codex.

This is agent-agnostic without promising that every unmodified agent works
automatically. A runtime either speaks the selected application protocol or is
fronted by an adapter, just as an MCP or ACP participant must implement its
respective protocol.

The showcase is not merely another AG-UI chat client. It demonstrates a modern
security boundary for a sensitive user-owned agent: the application can lend
temporary tools without installing them globally, the gateway can prevent
unauthorized subscription use, and the application can verify the enrolled
runtime before disclosing prompts, data, or tool results.

## Important compatibility questions

- Does the official TypeScript client support the browser-only, framework-light
  SDK shape the project wants?
- Can frontend tool results resume the same live OmniGENT/Codex turn without
  violating AG-UI run semantics?
- How should AG-UI `threadId`, `runId`, and tool-call identifiers map to the
  gateway's logical session, provider session, and stable action ID?
- Can fixed downstream tool snapshots coexist cleanly with AG-UI tools supplied
  per run?
- What is the minimum declared AG-UI compatibility profile, and how will
  unsupported state, generative UI, multimodal, and interrupt features fail?
- Can the security envelope remain orthogonal rather than forking AG-UI event
  schemas?
- Which AG-UI version and compatibility policy are stable enough for a public
  SDK?

## Conclusion

AG-UI is the strongest current candidate for the application-facing standard.
Adoption remains conditional on a real adapter spike. The project should not
replace the passing OmniGENT transport, claim AG-UI conformance, or supersede
the ACP decision until the compatibility questions are exercised through the
live browser-to-Codex tool loop.
