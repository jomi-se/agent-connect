What runs where

Three local processes participate, each with a distinct responsibility:

Process 1 OmniGENT server Owns conversations on loopback.
Process 2 OmniGENT host Keeps this VM available to launch Codex runners.
Process 3 Agent Connect gateway Listens on 127.0.0.1:8788.

Tailscale Serve exposes the gateway as HTTPS on port 8443. The Firebase app remains at agent-connect-demo.web.app. This VM currently routes :8443 to 127.0.0.1:8788. Because the generic gateway default is 8787, the command below sets port 8788 explicitly.

3Start the connector gateway

Use a new state filename for the first auth proof. Reusing it later preserves connector identity, enrolled devices, and grants. Do not delete an old state file just to rerun the demo; choose another filename when a clean enrollment is required.

Do not rely on an old SSH pseudo-terminal Run the gateway in another tmux window or under a supervisor. On this VM, a transient user service can be followed with journalctl --user -fu agent-connect-gateway.
Save the first-start output On first creation of the state file, the gateway prints a public runtime card, which may be pasted into the application, and a separate enrollment passphrase, which belongs only on the connector-owned consent page. Save the passphrase in a password manager.

The implementation cannot currently re-export the enrollment passphrase. Runtime-card re-export and credential rotation remain pending operator features.

Phone happy-path proof

  1. Open agent-connect-demo.web.app on a phone signed into the allowlisted tailnet.
  2. Paste only the public runtime card and submit the default task.
  3. If the browser asks to access local-network devices, allow it. Record this UX friction: a public Firebase page is contacting a private tailnet endpoint.
  4. Confirm navigation to the connector's *.ts.net:8443 page.
  5. Inspect the exact requesting origin, callback, scopes, and set_page_message schema. Enter the enrollment passphrase there and allow the request.
  6. Confirm return to Firebase, streamed Codex output, a tool.requested/tool.completed pair, and a visible page change.
  7. Open the connector grant list, revoke the Canvas grant, then submit again. The existing capability must be rejected.
Capture proof, not secrets Record the connector origin, consent, return redirect, tool event, page mutation, grant list, and rejected post-revocation request. Do not capture the passphrase, grant token, Codex login, or connector private state.
Troubleshooting the consent POST If consent returns {"error":"authorization_origin_mismatch"}, the gateway is still running the pre-fix build. Rebuild and restart only the gateway, return to Firebase, and begin authorization again. The enrollment passphrase and durable connector state do not change.
Enrolled, but Allow appears stuck The gateway is running the intermediate build whose CSP blocked the redirect back to Firebase. Apply the latest build and restart only the gateway. Return to Firebase and start a fresh authorization; do not enter or rotate the enrollment passphrase again.

Negative and restart checks

After the happy path, run these checks in order:

  1. Restart only the gateway with the same state path. Connector identity and revocation must survive.
  2. Retry from an unallowlisted Origin and confirm CORS/auth rejection.
  3. Change the application's tool snapshot and confirm the old grant cannot authorize it.
  4. Replay an already exchanged authorization callback and confirm rejection.
  5. Stop the OmniGENT host and confirm a task fails closed instead of silently selecting an unknown runtime. Restart it and confirm gateway-owned session healing provisions a healthy downstream session.
Prioritize the essential proof Do not block the first run on every negative case. Record the happy path and revocation first, then diagnose failures one boundary at a time.
